# 要件定義書

## はじめに

SpliTripは、旅行やイベント時の立替精算を管理する軽量Webアプリケーションです。本アプリケーションは、認証なしで旅行の作成、メンバー登録、柔軟な分割オプションでのレシート記録、精算サマリーの表示を可能にします。システムはURL共有方式を採用し、データはCloudflare Workers KVに保存されます。

## 用語集

- **旅行**: 共有経費イベントを表すメンバーとレシートの集合
- **メンバー**: 旅行の参加者で、レシートの支払いまたは負担をする人
- **レシート**: 1人のメンバーが支払い、選択されたメンバー間で分割される経費の記録
- **分割モード**: レシート金額を分割する方法（一律割、比率配分、金額指定配分）
- **精算**: 各メンバーが支払った金額と負担すべき金額の差額を示す計算結果
- **旅行ID**: URLを通じて旅行にアクセスするための一意の識別子
- **差額**: メンバーが支払った金額と負担すべき金額の差（全メンバーの合計は必ずゼロ）
- **システム**: SpliTripアプリケーション
- **管理ページ**: 旅行を作成・管理するページ
- **旅行ページ**: 旅行の詳細とナビゲーションを表示するページ
- **レシート入力ページ**: 新しいレシートを作成するページ
- **レシート編集ページ**: 既存のレシートを修正するページ
- **精算ページ**: 精算計算を表示するページ
- **メンバー精算詳細ページ**: 特定のメンバーの立替一覧と負担一覧を表示するページ
- **KVストア**: Cloudflare Workers KVストレージシステム
- **API**: Cloudflare Pages FunctionsのAPIエンドポイント

## 要件

### 要件1: 旅行の作成と管理

**ユーザーストーリー:** 旅行の主催者として、旅行を作成してメンバーを登録したい。そうすることで、グループの共有経費を追跡できる。

#### 受入基準

1. ユーザーが旅行名を指定して旅行を作成したとき、システムは一意の旅行IDを生成し、旅行をKVストアに保存しなければならない
2. 旅行が作成されたとき、システムは空のメンバーリストと空のレシートリストで初期化しなければならない
3. ユーザーが旅行にメンバーを追加したとき、システムは一意のメンバーIDを割り当て、旅行のメンバーリストに追加しなければならない
4. 旅行がURLを通じてアクセスされたとき、システムは旅行IDを使用してKVストアから旅行データを取得しなければならない
5. システムは各旅行のバージョン番号を維持し、更新のたびにインクリメントしなければならない
6. ユーザーが旅行を削除したとき、システムはKVストアから旅行データを削除しなければならない

### 要件2: 分割モード付きレシート入力

**ユーザーストーリー:** 旅行メンバーとして、柔軟な分割オプションでレシートを記録したい。そうすることで、各経費について誰が何を負担するかを正確に追跡できる。

#### 受入基準

1. ユーザーがレシートを作成するとき、システムは合計金額、支払い者の選択、分割設定を要求しなければならない
2. ユーザーが対象として「全メンバー」を選択したとき、システムは分割計算に登録されているすべてのメンバーを含めなければならない
3. ユーザーが対象として特定のメンバーを選択したとき、システムは分割計算に選択されたメンバーのみを含めなければならない
4. ユーザーが一律割モードを選択したとき、システムは合計金額を対象メンバー間で均等に分割しなければならない
5. ユーザーが比率配分モードを選択したとき、システムは提供されたパーセンテージ比率に基づいて合計金額を比例配分しなければならない（各メンバーの比率を合計した分母で各メンバーの比率を割って配分する）
6. ユーザーが金額指定配分モードを選択したとき、システムは各メンバーに指定された正確な金額を割り当てなければならない
7. 金額指定が提供されたとき、システムは金額指定の合計がレシートの合計金額と等しいことを検証しなければならない
8. システムは分割結果をメンバーIDと金額のペアの配列としてレシートに保存しなければならない

### 要件3: レシート編集

**ユーザーストーリー:** 旅行メンバーとして、既存のレシートを編集したい。そうすることで、間違いを修正したり経費の詳細を更新できる。

#### 受入基準

1. ユーザーがレシート一覧を表示したとき、システムはすべてのレシートをタイトル、金額、支払い者とともに表示しなければならない
2. ユーザーが編集するレシートを選択したとき、システムはレシートの現在のデータを編集フォームに読み込まなければならない
3. ユーザーがレシートを更新したとき、システムは新しい設定に基づいて分割金額を再計算しなければならない
4. レシートが更新されたとき、システムはレシートのupdatedAtタイムスタンプを更新しなければならない

### 要件4: 精算計算

**ユーザーストーリー:** 旅行メンバーとして、精算サマリーを表示したい。そうすることで、誰が何を支払い、誰が何を負担するかを確認できる。

#### 受入基準

1. 精算を計算するとき、システムはすべてのレシートにわたって各メンバーが支払った金額を合計しなければならない
2. 精算を計算するとき、システムはすべてのレシート分割にわたって各メンバーが負担する金額を合計しなければならない
3. 精算を計算するとき、システムは各メンバーの差額を支払い合計から負担合計を引いた値として計算しなければならない
4. システムはすべてのメンバーの差額の合計がゼロであることを保証しなければならない
5. 精算を表示するとき、システムは正の差額を受取金額として、負の差額を支払金額として表示しなければならない

### 要件5: メンバー別精算詳細

**ユーザーストーリー:** 旅行メンバーとして、特定のメンバーの詳細な精算情報を表示したい。そうすることで、支払いと負担の内訳を確認できる。

#### 受入基準

1. ユーザーがメンバーの精算詳細を表示したとき、システムはそのメンバーが支払ったすべてのレシートをタイトルと金額とともに表示しなければならない
2. ユーザーがメンバーの精算詳細を表示したとき、システムはそのメンバーが負担するすべてのレシート分割をタイトルと金額とともに表示しなければならない
3. メンバー詳細を表示するとき、システムはメンバーの支払い合計金額を表示しなければならない
4. メンバー詳細を表示するとき、システムはメンバーの負担合計金額を表示しなければならない
5. メンバー詳細を表示するとき、システムはメンバーの差額を表示しなければならない

### 要件6: データ永続化

**ユーザーストーリー:** システム管理者として、旅行データが確実に保存・取得されることを望む。そうすることで、ユーザーがいつでも経費情報にアクセスできる。

#### 受入基準

1. 旅行が作成または更新されたとき、システムは旅行データをJSON形式にシリアライズしなければならない
2. 旅行データを保存するとき、システムはKVストアで「trip:{tripId}」のキー形式を使用しなければならない
3. 旅行データを取得するとき、システムはKVストアからJSONをデシリアライズしてTripオブジェクトに変換しなければならない
4. 旅行が更新されたとき、システムは保存前にバージョン番号をインクリメントしなければならない
5. システムは旅行作成、旅行更新、メンバー作成、レシート作成、レシート更新のタイムスタンプを保存しなければならない

### 要件7: URLベースの共有

**ユーザーストーリー:** 旅行の主催者として、URLを通じて旅行を共有したい。そうすることで、メンバーが認証なしで旅行にアクセスできる。

#### 受入基準

1. 旅行が作成されたとき、システムは旅行IDを含む共有可能なURLを生成しなければならない
2. ユーザーが旅行URLにアクセスしたとき、システムは認証を要求せずに旅行データを読み込まなければならない
3. システムは旅行IDを含むURLパスを通じて、レシート入力、レシート編集、精算ページへのナビゲーションをサポートしなければならない

### 要件8: 分割計算の正確性

**ユーザーストーリー:** 開発者として、分割計算が正確で一貫していることを望む。そうすることで、精算の差額が常にゼロになる。

#### 受入基準

1. 一律割を計算するとき、システムは合計金額を対象メンバー数で割らなければならない
2. 比率配分を計算するとき、システムは各メンバーの分担額を「合計 * (メンバー比率 / 全比率の合計)」として計算しなければならない
3. 金額指定配分を計算するとき、システムは各メンバーに提供された正確な金額を使用しなければならない
4. 分割が端数を生じるとき、システムは端数をレシート分割時に処理し、任意の1人のメンバーに端数を寄せなければならない
5. 旅行内のすべてのレシートについて、すべての分割金額の合計はすべてのレシート合計金額の合計と等しくなければならない
6. システムはメンバーの途中追加を考慮せず、レシート入力時点のメンバー選択に基づいて分割を確定しなければならない

### 要件9: APIエンドポイント

**ユーザーストーリー:** フロントエンド開発者として、明確に定義されたAPIエンドポイントが欲しい。そうすることで、UIをバックエンドストレージと統合できる。

#### 受入基準

1. システムは新しい旅行を作成するために/api/tripsにPOSTエンドポイントを提供しなければならない
2. システムは旅行データを取得するために/api/trips/:tripIdにGETエンドポイントを提供しなければならない
3. システムは旅行データを更新するために/api/trips/:tripIdにPUTエンドポイントを提供しなければならない
4. PUTリクエストを受信したとき、システムはKVストア内の旅行JSON全体を置き換えなければならない
5. APIリクエストが失敗したとき、システムは適切なHTTPステータスコードとエラーメッセージを返さなければならない

### 要件10: モバイル最適化UI

**ユーザーストーリー:** モバイルユーザーとして、スマートフォン画面に最適化されたインターフェースが欲しい。そうすることで、外出先で簡単に経費を管理できる。

#### 受入基準

1. アプリケーションがモバイルデバイスでアクセスされたとき、システムは小さな画面に最適化されたレスポンシブレイアウトを表示しなければならない
2. フォームを表示するとき、システムはモバイルフレンドリーな入力コントロールを使用しなければならない
3. リストを表示するとき、システムはタッチフレンドリーなタップターゲットを使用しなければならない
4. システムは一般的なタスクを完了するために必要なステップ数を最小限に抑えなければならない
5. エラーが発生したとき、システムは明確で簡潔なエラーメッセージを表示しなければならない

### 要件11: 比率配分のデフォルト値

**ユーザーストーリー:** 旅行メンバーとして、比率入力がデフォルトで100%になっていてほしい。そうすることで、手動入力なしで素早く均等分割を作成できる。

#### 受入基準

1. ユーザーが比率配分モードを選択したとき、システムはすべてのメンバー比率を100に初期化しなければならない
2. ユーザーがメンバーの比率を変更したとき、システムは変更された値を保持しなければならない
3. 比率配分を計算するとき、システムは任意の正の比率値を受け入れなければならない

### 要件12: データ検証

**ユーザーストーリー:** 開発者として、入力データが検証されることを望む。そうすることで、無効なデータがシステム状態を破壊できない。

#### 受入基準

1. ユーザーが旅行を作成するとき、システムは空でない旅行名を要求しなければならない
2. ユーザーがメンバーを追加するとき、システムは空でないメンバー名を要求しなければならない
3. ユーザーがレシートを作成するとき、システムは正の合計金額を要求しなければならない
4. ユーザーがレシートを作成するとき、システムはメンバーリストからの有効な支払い者IDを要求しなければならない
5. ユーザーがレシートの特定のメンバーを選択するとき、システムは少なくとも1人のメンバーが選択されることを要求しなければならない
6. ユーザーが金額指定を提供するとき、システムは合計が合計金額と等しくない場合にレシートを拒否しなければならない
7. ユーザーが比率を提供するとき、システムはすべての比率が正の数であることを要求しなければならない
